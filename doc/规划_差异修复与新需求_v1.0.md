## 2. OTA 固件升级系统 (Detailed Specs)

### 2.1 版本号规范
- **格式**: `A.B.C.D` (4位数字)
- **约束**: 每一位数字范围为 `0-99`。
- **示例**: `1.0.0.1` -> `1.0.0.99` -> `1.0.1.0`

### 2.2 更新逻辑
- **不可回退**: 新上传固件的版本号必须 **严格大于 (Strictly Greater)** 当前数据库中最新固件的版本号。
- **Web 端校验**: 管理员上传固件时，后端必须解析固件头或文件名中的版本号，与数据库比对。若版本号 <= 当前最新版，拒绝上传。

### 2.3 上传与安全
- **上传权限**: 仅限超级管理员 (Super Admin)。
- **安全建议 (加密/验证方式)**:
    1.  **传输层**: 强制 HTTPS，防止传输篡改。
    2.  **身份验证**: 使用现有的 **JWT Admin Token**，增加 IP 白名单(可选)。
    3.  **固件完整性 (Integrity)**:
        - 管理员上传时，后端计算 **SHA-256 Checksum** 并存储。
        - 设备端下载时，需校验 Checksum 确保文件未损坏。
    4.  **【建议】固件签名 (Firmware Signing)**:
        - *这是最安全的做法*：开发者在本地使用私钥 (Private Key, e.g., Ed25519) 对固件进行签名。
        - 后端仅存储固件和签名文件，不掌握私钥。
        - 设备端烧录公钥 (Public Key)，在刷写固件前验证签名。
        - *实施建议*: 考虑到开发成本，第一阶段可先在 Backend 做 SHA-256 校验，第二阶段引入数字签名。

### 2.4 数据表设计建议
- `firmwares` 表: `id`, `version_code` (INT, eg 10000001), `version_str`, `file_path`, `checksum`, `created_at`.

## 3. 激活与初始化流程重构 (Activation Flow)

### 3.1 前端 "三步走" 引导 (Web App)
将 `SetupPage` 重构为向导式流程：

1.  **Step 1: 建立连接 (激活)**
    - 输入/扫码获取设备码与初始密码。
    - 验证通过后，设置用户登录密码。
2.  **Step 2: 注入灵魂 (档案)**
    - **强制步骤**。用户必须填写生辰八字、职业、昵称。
    - 只有完成此步骤，才能进入下一步。
3.  **Step 3: 启动 (完成)**
    - 显示 "激活成功" 动画。
    - 引导用户在设备端按下按钮开始使用。
    - 跳转至 Web 首页 (Profile/Dashboard)。

### 3.2 二维码生成 (Backend/Device)
- **设备端**: 屏幕显示配网/激活二维码。
    - 内容格式: `https://talisman.app/setup?code=ABC123&pwd=XYZ789` (包含明文初始密码以便一键填充，需权衡安全性)。
- **后端校验**:
    - 在 Step 1 提交激活请求时，后端验证 `device_code` 和 `init_password` 的匹配性（基于 HMAC 盐值计算）。
    - 移除前端对 URL `sig` 的复杂校验，改为后端统一处理。
